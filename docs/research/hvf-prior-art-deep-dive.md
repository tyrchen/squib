# HVF Prior Art Deep Dive — Architecture Reference for squib

This document is the result of reading the source of the two most relevant Rust HVF VMM projects — `containers/libkrun` and the `cloud-hypervisor` ecosystem — plus lighter passes on `google/alioth`, `rust-vmm/vmm-reference`, and `containers/krunvm`. The goal is to extract architecture, file layout, and concrete patterns so squib can borrow rather than reinvent. All file paths cited are absolute paths *inside the upstream repos* and serve as pointers to read alongside this doc.

The headline corrections to the original brief: **libkrun is Apache-2.0**, not LGPL-2.1 (verified via the GitHub `repos/containers/libkrun/license` API; the LICENSE file is the standard Apache 2.0 text). This dramatically changes the borrow-vs-build calculus — libkrun is freely copyable code, not a study-only reference. Also: the **`cloud-hypervisor/hypervisor-framework` crate is dormant** (last meaningful commit 2022-01-26, predates `hv_gic_*` by three years) and **cloud-hypervisor itself has zero HVF integration** in tree (the `hypervisor` crate has only `kvm/` and `mshv/` backends). What was advertised as a "second Rust HVF VMM" effectively does not exist as a usable artifact in 2026.

## 1. libkrun — deep dive

libkrun 1.18.0 (released 2026-04-24) is the only mature, actively-maintained, native-macOS, Rust microVM monitor. It is also the closest in shape to what squib wants to be — a Firecracker-derived VMM with a swappable hypervisor backend, virtio-MMIO devices, an FDT, and an aarch64 boot path.

### 1.1 Workspace layout

The repo is a Cargo workspace with 15 member crates under `src/`:

```
src/
  arch/          arch-specific layout, boot, sysreg setup (aarch64, x86_64, riscv64)
  arch_gen/      generated bindings (ELF, bootparam, etc.)
  aws_nitro/     AWS Nitro enclaves variant (TEE)
  cpuid/         x86_64 CPUID masking
  devices/       MMIO bus, legacy devices, FDT, virtio device implementations
  display/       virtio-gpu display backend
  hvf/           Hypervisor.framework backend (the file we care about most)
  input/         virtio-input
  kernel/        kernel loader + cmdline (loader/aarch64.rs, loader/riscv64.rs, mod.rs)
  libkrun/       the C-ABI shim that ships as the dylib
  polly/         epoll/kqueue event loop
  rutabaga_gfx/  3D virtio-gpu (forked from crosvm)
  smbios/        SMBIOS table builder (x86_64)
  utils/         shared utilities
  vmm/           VMM core: builder, vstate, device_manager, signal_handler, terminal
```

Hypervisor backend selection is **compile-time per OS**. There is no runtime trait-object polymorphism: `src/vmm/src/linux/` and `src/vmm/src/macos/` are sibling directories selected by `cfg(target_os)`. The macOS side has only two files: `mod.rs` and `vstate.rs`. The KVM/HVF split happens by replacing the vCPU state machine wholesale, not by a thin trait.

The dedicated `src/hvf/` crate (package name `krun-hvf`) is a thin Rust wrapper over `bindgen`-generated FFI: `src/hvf/src/bindings.rs` is auto-generated by rust-bindgen 0.70.1 against Apple's `Hypervisor.h`, and `src/hvf/src/lib.rs` provides the safe `HvfVm` and `HvfVcpu<'a>` types, the `VcpuExit<'a>` enum, the `Vcpus` callback trait, and the syndrome-decode logic. **It is not based on `applevisor`** — libkrun rolls its own bindings and dynamically loads `Hypervisor.framework` via `libloading::Library` at runtime (`static HVF: LazyLock<libloading::Library>` pointing to `/System/Library/Frameworks/Hypervisor.framework/Versions/A/Hypervisor`). This is unusual; `applevisor` would have given them static linking against a versioned crate. The dynamic-loading choice is presumably to ease cross-version probing and avoid hard build-time dependence on Xcode SDKs.

### 1.2 The HVF backend in detail

`src/hvf/src/lib.rs` is the heart of the macOS port. The exported surface is small and clean:

- `HvfVm` — wraps `hv_vm_create`, `hv_vm_config_create`, `hv_vm_config_set_el2_enabled`, `hv_vm_map`/`hv_vm_unmap`. Memory mapping is done with three permission bits assembled from `HV_MEMORY_READ | HV_MEMORY_WRITE | HV_MEMORY_EXEC`.
- `HvfVcpu<'a>` — wraps `hv_vcpu_create`, `hv_vcpu_run`, `hv_vcpu_get_reg`/`set_reg`, `hv_vcpu_get_sys_reg`/`set_sys_reg`, `hv_vcpu_set_pending_interrupt`, `hv_vcpu_set_vtimer_mask`, plus `hv_vcpus_exit` for cross-thread cancellation.
- `VcpuExit<'a>` — the unified exit enum: `Breakpoint`, `Canceled`, `CpuOn { mpidr, entry, context_id }`, `HypervisorCall`, `MmioRead(pa, &mut [u8])`, `MmioWrite(pa, &[u8])`, `PsciHandled`, `SecureMonitorCall`, `Shutdown`, `SystemRegister`, `VtimerActivated`, `WaitForEvent`, `WaitForEventExpired`, `WaitForEventTimeout(Duration)`.
- `Vcpus` trait — vCPU-list callback with `set_vtimer_irq()`, `has_pending_irq()`, `handle_sysreg_read()`, `handle_sysreg_write()`. The trait is held as `Arc<dyn Vcpus>` and passed into `HvfVcpu::run()` so that PSCI CPU_ON, sysreg traps, and inter-vCPU IRQ injection can call back into the VMM without the HVF crate owning that state.

The vCPU run loop in `HvfVcpu::run(&mut self, vcpu_list: Arc<dyn Vcpus>) -> VcpuExit` looks like this in essence:

1. **Pre-run housekeeping.** If a previous exit was a pending MMIO read, write the loaded value back to the destination GP register via `hv_vcpu_set_reg`. If `pending_advance_pc` is set, advance PC by 4. If `vcpu_list.has_pending_irq()` is true, call `hv_vcpu_set_pending_interrupt(IRQ)`.
2. **Run.** Call `hv_vcpu_run`; on return, switch on `self.vcpu_exit.reason`:
   - `HV_EXIT_REASON_VTIMER_ACTIVATED` → `VtimerActivated`, mark `vtimer_masked = true` (and the VMM is responsible for unmasking via `hv_vcpu_set_vtimer_mask` once the guest acknowledges).
   - `HV_EXIT_REASON_CANCELED` → `Canceled` (used for clean shutdown).
   - `HV_EXIT_REASON_EXCEPTION` → ESR_EL2 decode, see below.
3. **Exception decode.** Read `ESR_EL2` from `vcpu_exit.exception.syndrome`, extract EC bits 31:26:
   - `EC_DATAABORT` (0x24) — extract ISV/ISWrite/SAS/SRT/CM bits, read FAR/HPFAR for the physical address, set `pending_advance_pc = true`, return `MmioRead` / `MmioWrite`.
   - `EC_AA64_HVC` (0x16) — call `handle_psci_request()`. PSCI dispatch on X0: 0x84000000 PSCI_VERSION → returns 2 in X0; 0x84000006 MIGRATE_INFO_TYPE; 0x84000008/9 SYSTEM_OFF/RESET → `Shutdown`; 0xC4000003 CPU_ON → reads MPIDR/entry/context_id and returns `CpuOn`.
   - `EC_AA64_SMC` (0x17) — advance PC, then identical PSCI path.
   - `EC_SYSTEMREGISTERTRAP` (0x18) — decode ISS, call `vcpu_list.handle_sysreg_read/write()`, advance PC, return `SystemRegister`.
   - `EC_WFX_TRAP` (0x1) — read `CNTV_CTL_EL0` and `CNTV_CVAL_EL0` to compute timer deadline, return `WaitForEvent` / `WaitForEventExpired` / `WaitForEventTimeout(Duration)` so the VMM thread can park accordingly.
   - `EC_AA64_BKPT` (0x3c) → `Breakpoint`.

This is the entire dispatch surface. Squib should adopt this exit enum and dispatcher essentially verbatim — it's well-shaped, exhaustively covers what HVF can throw, and is Apache-2.0.

### 1.3 vCPU thread, MMIO bus, vstate

`src/vmm/src/macos/vstate.rs` defines `Vcpu` (the per-thread VMM-side struct) and the run loop:

- `start_threaded()` spawns a dedicated OS thread per vCPU (mandatory because of HVF's thread affinity contract — every `hv_vcpu_*` call must come from the thread that called `hv_vcpu_create`).
- The thread's `run()` method calls `run_emulation()` in a loop, matching on `VcpuEmulation` (the VMM-side wrapper around `VcpuExit`). For MMIO it does `if let Some(ref mmio_bus) = self.mmio_bus { mmio_bus.read(vcpuid, addr, data); }`.
- `memory_init()` walks the `GuestMemoryMmap` regions (rust-vmm) and calls `self.hvf_vm.map_memory(host_addr as u64, region.start_addr().raw_value(), region.len())` for each.

The MMIO bus is in `src/devices/src/bus.rs`: `BTreeMap<BusRange, Arc<Mutex<dyn BusDevice>>>` with `first_before(addr)` for log-N lookup. The `BusDevice` trait has `read`, `write`, `interrupt`. This is the same shape as Firecracker's bus, lightly evolved.

### 1.4 GIC: in-kernel vs userspace, both shipped

libkrun is one of the very few projects that has done the in-kernel HVF GICv3 work. Two parallel implementations live in `src/devices/src/legacy/`:

- **`hvfgicv3.rs`** — the new path, landed 2025-03-10. Dynamically loads `hv_gic_create`, `hv_gic_config_create`, `hv_gic_set_spi`. The struct `HvfGicV3` has `new(vcpu_count)`, `device_properties()` (returns distributor+redistributor base+size for the FDT), `fdt_compatibility()` returning `"arm,gic-v3"`, and `set_irq()` that calls `hv_gic_set_spi(irq_line, true)`. Distributor/redistributor MMIO is handled in-kernel by the framework — there is no userspace register emulation. Requires macOS 15 Sequoia or later.
- **`gicv3.rs`** — the legacy fallback for macOS 14 Sonoma. A pure-userspace GICv3 distributor + redistributor emulator: `GicV3` struct with `handle_dist_read32/write32/write64()`, `handle_redist_read32/read64/write32()`, plus `set_irq()` doing MPID extraction and routing. Helper functions `half_shuffle32`/`half_unshuffle32` for edge-trigger encoding.

For squib's macOS-15+/Apple-Silicon-only stance, **only `hv_gic_*` matters**. Don't carry the userspace fallback.

### 1.5 Memory management — no dirty tracking

libkrun maps guest memory once via `hv_vm_map` per `GuestMemoryMmap` region and never does anything cleverer. There is **no software dirty-bit tracking** in the libkrun codebase — a search for "dirty" in `src/` returns nothing structural. Snapshots are not implemented (the literal string "snapshot" appears in only six `.rs` files, and none of them are a snapshot path; they are comments/cases in TEE prep code or virtio queue code). This is a real gap if squib wants Firecracker-style snapshot/restore. See §6.

### 1.6 Boot path on aarch64

Memory layout from `src/arch/src/aarch64/layout.rs`:

```
DRAM_MEM_START_KERNEL = 0x8000_0000  (2 GiB — kernel + initrd live here)
DRAM_MEM_START_EFI    = 0x4000_0000  (1 GiB — EFI variant)
DRAM_MEM_END          = 0x00FF_8000_0000
MAPPED_IO_START       = 0x0a00_0000  (devices below this; GIC at lower offsets)
SMBIOS_START          = 0x4000_F000
IRQ_BASE              = 32           (first SPI; PPI is 0..31)
IRQ_MAX               = 159
VTIMER_IRQ            = 27           (PPI 11)
RESET_VECTOR          = 0x0
```

Kernel loading lives in `src/kernel/src/loader/`. Files: `aarch64.rs`, `riscv64.rs`, `mod.rs`. On aarch64 it loads raw `Image` (the ARM64 boot executable header form) — there is no `Image.gz`, `Image.bz2`, `Image.zstd` decompression path on aarch64; those exist for x86_64 only. This is squib's first reason to build a slightly richer kernel loader: Linux distros commonly ship gzipped Images, and asking users to `gunzip` first is a UX papercut.

The FDT is built by `src/devices/src/fdt/aarch64.rs` using **rust-vmm's `vm-fdt` crate** (a real dependency, not a fork). `create_fdt()` calls a sequence of node builders: `create_cpu_nodes()` (one cpu@N per vCPU with MPIDR), `create_memory_node()`, `create_chosen_node()` (bootargs + initrd-start/end + stdout-path), `create_gic_node()` (with the addresses returned by `HvfGicV3::device_properties()`), `create_timer_node()` with PPI numbers, `create_clock_node()` (24 MHz fixed), `create_psci_node()`, then `create_devices_node()` which builds `create_gpio_node()` (for the PSCI power button), `create_rtc_node()`, `create_serial_node()`, and `create_virtio_node()` for each virtio-MMIO device sorted by base address.

Initial vCPU state in `src/arch/src/aarch64/macos/regs.rs`: PC = kernel entry, X0 = FDT physical address, PSTATE configured for EL1h with masked DAIF (the standard aarch64 Linux boot ABI). On nested setups, additional HCR_EL2 / CNTHCTL_EL2 setup happens conditionally.

### 1.7 Devices

Under `src/devices/src/virtio/`: `block/`, `console/`, `fs/` (virtio-fs), `gpu/`, `input/`, `net/`, `rng/`, `snd/`, `vsock/`, `balloon/`. The virtio-MMIO transport is in `src/devices/src/virtio/mmio.rs`: it depends on **rust-vmm `vm-memory = 0.17`, `vmm-sys-util = 0.14`, `linux-loader = 0.13.2`** (and `kvm-bindings = 0.12`, `kvm-ioctls = 0.22` on Linux only). Notably libkrun does **not** depend on `virtio-queue` from rust-vmm — it has its own `queue.rs` and `descriptor_utils.rs`. That looks historical (Firecracker also forked the queue code originally) and is worth noting: most of the device wiring around the queue is libkrun's own, not rust-vmm.

The vsock implementation (`vsock/`) is unusually rich: `muxer.rs`, `proxy.rs`, `tsi_dgram.rs`, `tsi_stream.rs`, `unix.rs`. libkrun runs **TSI (Transparent Socket Impersonation)** — the guest opens AF_VSOCK sockets and libkrun proxies them transparently to host AF_INET/AF_UNIX. This is an architecture squib will want eventually (it's how `krunvm` makes containers feel like containers), but it's a non-trivial port.

### 1.8 Snapshots, perf, license, pace

- **Snapshots:** not implemented. Confirmed via repo-wide code search.
- **Perf:** RedHat blogs (Sergio Lopez) emphasize end-to-end inference numbers, not VMM micro-benchmarks. The widely-cited "125 ms boot on M3" number is from a Medium article by `u3n` and is **Lima-nested-Firecracker, not native macOS**: macOS → Lima Linux VM → Firecracker. That's a useful upper bound for what users *expect* but is not a real native HVF measurement. No published native-HVF "Firecracker-class" boot number for libkrun exists. Realistic native HVF cold-start for a small Linux microVM is in the 200–500 ms range based on community reports; squib should plan to measure this from day 1 rather than promise 125 ms.
- **License: Apache-2.0, confirmed.** This means squib can freely copy code, patterns, and architecture from libkrun. Practically: copy `src/hvf/src/lib.rs`'s exit dispatcher, copy `src/devices/src/legacy/hvfgicv3.rs`, copy the FDT builder, copy the bus, copy the vsock TSI architecture — all clean. Attribution in NOTICE.
- **Maintainership:** Sergio Lopez Pascual (Red Hat) is the primary maintainer. Active commits through April 2026 (1.18.0 released 2026-04-24). The HVF-specific path is alive: the in-kernel GIC PR landed 2025-03-10, the file received Rust-version maintenance commits in 2025-08, and the package is being modernised in April 2026 for crates.io publication. Healthy.

## 2. cloud-hypervisor — investigation result: not a viable starting point

cloud-hypervisor is the project most often suggested as "the cleaner architectural alternative to libkrun." After reading the source, **for HVF this is not true today**:

### 2.1 HVF integration status: nonexistent in tree

`hypervisor/src/` contains `kvm/`, `mshv/`, `arch/`, and the trait files (`hypervisor.rs`, `vm.rs`, `cpu.rs`, `device.rs`). **There is no `hvf/` directory.** A code search for "hvf" or "hypervisor_framework" across the entire `cloud-hypervisor/cloud-hypervisor` repo returns essentially nothing. The project's GitHub roadmap board makes no public commitment to adding HVF. There is no feature flag, no experimental branch, no `[cfg(target_os = "macos")]` block in the hypervisor crate. The mainline VMM crate likewise has no macOS-conditional code paths I could find.

### 2.2 The `hypervisor-framework` crate: dormant

The companion repo `cloud-hypervisor/hypervisor-framework` is a separate workspace with two crates (`hv-sys` for raw FFI, `hv` for safe wrappers). **Last meaningful commit: 2022-01-26**. Everything since is metadata. The crate has 51 GitHub stars, 1 open issue, 6 forks. It predates `hv_gic_*` (macOS 15, 2024) by three years and has no coverage of the in-kernel GIC, EL2 nested virt, or SME state save/restore APIs. The `hv` crate exposes `Vcpu`, `Vm`, `Memory` bitflags, `Error` enum, a `call!` macro, and re-exports `hv_sys`. It's a half-finished safe wrapper that nobody is integrating.

For squib this means the practical option in the cloud-hypervisor world is: **fork the trait shape, write the HVF backend yourself.** That's not zero work, but the trait shape is genuinely cleaner than libkrun's compile-time `cfg`-split.

### 2.3 The Hypervisor / Vm / Vcpu traits — KVM-shaped, awkward fit

From `cloud-hypervisor/hypervisor/src/hypervisor.rs`:

```rust
pub trait Hypervisor: Send + Sync {
    fn hypervisor_type(&self) -> HypervisorType;
    fn create_vm(&self, config: HypervisorVmConfig) -> Result<Arc<dyn Vm>>;
    #[cfg(target_arch = "x86_64")]
    fn get_supported_cpuid(&self) -> Result<Vec<CpuIdEntry>>;
    fn check_required_extensions(&self) -> Result<()>;
    #[cfg(target_arch = "aarch64")]
    fn get_host_ipa_limit(&self) -> i32;
    fn get_max_vcpus(&self) -> u32;
    // ... TDX, AMX, debug breakpoints
}
```

The Vcpu trait's aarch64 surface includes `vcpu_init(&VcpuInit)`, `vcpu_set_processor_features`, `get_reg_list`, `get_sys_reg`, `setup_regs(cpu_id, boot_ip, fdt_start)`, `init_pmu(irq)`, `set_gic_redistributor_addr` — all direct mirrors of KVM ioctls. **`VcpuInit`** is literally the KVM struct. An HVF impl can plausibly satisfy these but most methods become awkward stubs (e.g., `get_reg_list` has no HVF analog), and there's no exit-enum equivalent that matches HVF's `hv_vcpu_exit_t`. The cloud-hypervisor `VmExit` enum is x86-flavored (IO ports, hyperv synic, paging fault), not aarch64-flavored.

### 2.4 What's worth borrowing anyway

Despite the HVF gap, cloud-hypervisor is Apache-2.0 and has cleanly separated, high-quality, KVM-tested implementations of:

- **virtio-MMIO and virtio-PCI transports** (`virtio-devices/src/transport/`).
- **virtio-block, virtio-net, virtio-rng, virtio-balloon, virtio-vsock** — clean rust-vmm-style impls. Better-tested than libkrun's equivalents.
- **vm-allocator, vm-device, vm-virtio, vm-migration** — the helper crates. `vm-allocator` is genuinely useful for IPA/MMIO allocation; squib should consume it from crates.io rather than copy.
- **PCI subsystem** — `pci/` crate. Not relevant for an MMIO-only Firecracker-shape, ignore.
- **API server** (`vmm/src/api/`) — the OpenAPI-driven REST server. Inspirational shape.

### 2.5 Practical license takeaway

cloud-hypervisor is **Apache-2.0 + BSD-3-Clause + CC-BY-4.0** (multi-licensed via REUSE; main code is Apache-2.0). Free to copy with attribution. Squib can lift virtio-block/net/rng impls almost verbatim if we want a faster path than libkrun's.

## 3. Lighter coverage

### 3.1 alioth (google/alioth) — cleanest trait design, partial HVF, experimental

Apache-2.0, 349 stars, last push 2026-05-01 (very active). Top-level: `alioth/`, `alioth-cli/`, `bootloader/`. Inside `alioth/src/`: `arch/`, `blk/`, `board/`, `cpu/`, `device/`, `firmware/`, `fuse/`, `hv/` (the hypervisor abstraction), `loader/`, `mem/`, `pci/`, `vfio/`, `virtio/`, `vm/`. The `hv/` subdir has both `hvf/` and `kvm/` backends. It uses **hand-rolled FFI** (calls `os_release` directly, not `applevisor`). Crucially, alioth's trait shape is genuinely cross-hypervisor by construction:

```rust
pub trait Hypervisor {
    type Vm: Vm + Sync + Send + 'static;
    fn create_vm(&self, config: &VmConfig) -> Result<Self::Vm>;
}
pub trait Vm {
    type Vcpu: Vcpu;
    type Memory: VmMemory;
    type IrqSender: IrqSender + Send + Sync;
    type MsiSender: MsiSender;
    type IoeventFdRegistry: IoeventFdRegistry;
    fn create_vcpu(&self, index: u16, identity: u64) -> Result<Self::Vcpu>;
    // ...
}
pub trait Vcpu {
    fn get_reg(&self, reg: Reg) -> Result<u64>;
    fn set_regs(&mut self, vals: &[(Reg, u64)]) -> Result<()>;
    fn run(&mut self, entry: VmEntry) -> Result<VmExit>;
}
```

**What it teaches us:** associated types (not `dyn Trait`) for the vCPU/Memory/IrqSender hierarchy, with `Reg` as a unified register enum and `VmEntry` parameterising the run call (so the same `run()` accepts either "MMIO read result" or "fresh start"). This is the right shape for squib if we want any chance of multi-backend testability. The disclaimer that "Alioth is an experimental project and is NOT an officially supported Google product" is real — its HVF backend is shallow (no in-kernel GIC, no PSCI dispatch shown), the README has no boot-time numbers, and it doesn't implement the breadth of devices libkrun has. But the **trait file `alioth/src/hv/hv.rs` is the single best architectural reference for squib's hypervisor abstraction.** Read it, port the shape, fill it with your own HVF code.

### 3.2 vmm-reference (rust-vmm/vmm-reference) — KVM-only, frozen

Apache-2.0, 165 stars. Last push **2024-09-09**. KVM-only, x86_64-focused, explicitly "experimental, not for production." Useful only as a worked example of how to glue rust-vmm crates (vm-memory, vm-allocator, virtio-queue, linux-loader, vm-fdt, kvm-ioctls, kvm-bindings) into a minimal VMM. It's the canonical "wiring" tutorial. **What it teaches us:** the rust-vmm component graph and how to compose them; specifically, how to fold linux-loader + vm-memory + vm-allocator into a sub-200-LOC boot path. Don't depend on it; do read its `src/vmm/` once.

### 3.3 krunvm (containers/krunvm) — wrapper, not VMM

Apache-2.0, 1658 stars, last push 2026-02-09. Written in Rust, but **it is not a VMM** — it's a CLI on top of `libkrun.dylib` that pulls OCI images, builds rootfs, and calls into libkrun's C ABI. **What it teaches us:** the libkrun C-ABI surface and how to drive it from a host CLI. If squib wants Firecracker-CLI parity, the way to expose squib's library to non-Rust embedders may be a similar `libsquib.dylib` with a stable C ABI; krunvm is the consumer-side reference for what such a library looks like in use.

## 4. Synthesis A — borrow-vs-build per subsystem

This table is squib-specific and opinionated. "Port" means lift code with attribution; "Adapt" means take the architecture but write fresh code; "Fresh" means no good prior art, design from scratch.

| Subsystem | Verdict | Source |
|---|---|---|
| Hypervisor binding (raw `hv_*` FFI) | **Adapt** | Use `applevisor` (crates.io, Apache-2.0) rather than dynamic-load like libkrun. Static linking is cleaner; the risk libkrun avoids (build-time SDK dependency) is minor for an Apple-Silicon-only project that already requires Xcode for codesign + entitlements. |
| vCPU run loop + ESR_EL2 dispatch | **Port from libkrun** | `src/hvf/src/lib.rs` `HvfVcpu::run` is excellent. Copy it; rename types; translate raw FFI calls to `applevisor`. Apache-2.0 attribution. |
| MMIO bus | **Port from libkrun or Firecracker** | libkrun's `BTreeMap<BusRange, Arc<Mutex<dyn BusDevice>>>` in `src/devices/src/bus.rs` is fine. Firecracker's is functionally identical. Either works. |
| Virtio-MMIO transport | **Port from cloud-hypervisor** | cloud-hypervisor's `virtio-devices/src/transport/mmio.rs` is cleaner-coded, better-tested, and uses upstream `virtio-queue` from rust-vmm. libkrun rolls its own queue, which is a maintenance tax we should not inherit. |
| virtio-block | **Port from cloud-hypervisor** | Use the rust-vmm `block` crate plus cloud-hypervisor's wiring. Mature, async-ready, supports multi-queue. |
| virtio-net | **Port from cloud-hypervisor** | Same reasoning. Plus we already need the macOS `vmnet`/`socket_vmnet` adapter; that part is squib-fresh. |
| virtio-vsock | **Port from libkrun** | libkrun's vsock with TSI is a substantial advantage for AWS-Lambda-shaped guests (sockets just work). cloud-hypervisor has plain virtio-vsock; libkrun has TSI on top. |
| virtio-balloon | **Port from cloud-hypervisor** | Trivial choice. Well-tested. |
| virtio-rng | **Port from cloud-hypervisor or fresh** | 50 LOC; either is fine. |
| GICv3 (HVF in-kernel) | **Port from libkrun** | `src/devices/src/legacy/hvfgicv3.rs`. The only Rust implementation in existence as of 2026. ~150 LOC, Apache-2.0. **Port verbatim modulo applevisor adaptation.** |
| FDT builder | **Port from libkrun** | `src/devices/src/fdt/aarch64.rs`. Uses `vm-fdt` crate. Cleanest shape for our needs. |
| Kernel loader | **Adapt + extend** | libkrun's `src/kernel/src/loader/aarch64.rs` only handles raw `Image`. Squib should extend with `Image.gz`, `Image.zst`, and PE32+ EFI. Use `linux-loader = 0.13` from rust-vmm as the base; add the decompression layer ourselves. |
| Snapshot serializer | **Fresh** | No prior art. libkrun has no snapshots. cloud-hypervisor has `vm-migration` but it's KVM-state-shaped. squib needs a fresh design: serialize HVF vCPU register state (general-purpose, FP/SIMD, system regs from `applevisor::Vcpu::sys_reg_get` over the full curated list), guest memory regions (mmap + write to file), virtio device state per-device, GIC state via `hv_gic_get_*` (macOS 15+). Format: borrow Firecracker's serde-based `MicrovmState` shape, encode with `bitcode + serde`. **Cross-host (KVM↔HVF) snapshot is out of scope.** |
| MMDS / dumbo TCP stack | **Port from Firecracker** | MMDS is Firecracker-specific (Apache-2.0). Lift the `dumbo/` and `mmds/` crates. They depend only on rust-vmm's `vm-memory` and a few helpers. |
| API server (Firecracker REST) | **Port from Firecracker** | Lift the OpenAPI-defined endpoints. Wire to squib's VMM core. |

Default hypervisor binding choice: **`applevisor` 1.0 with `macos-26-0`** as the default feature, with squib's own thin trait wrapper on top so we can swap to alioth-style hand-rolled FFI later if `applevisor` goes stale. Reason: `applevisor` is current with the Tahoe APIs (Sept 2025), is by Impalabs (a well-known security research outfit), and saves us from writing 1500 LOC of bindgen glue. The bus-factor risk (single maintainer) is real and should be mitigated by keeping all `hv_*` calls behind a `squib-hv` internal crate — if we ever need to fork applevisor we can do so cleanly.

## 5. Synthesis B — recommended squib crate layout

Adopting alioth's trait shape, libkrun's HVF code, and cloud-hypervisor's virtio devices, squib should be a Cargo workspace under `crates/` that looks like:

```
crates/
  squib-hv/             # safe HVF bindings (wraps applevisor)
                        #   - HvVm, HvVcpu, VcpuExit, hv_gic_* wrappers
                        #   - exposes async-friendly surface
  squib-arch/           # aarch64-specific layout, sysreg helpers, boot regs
                        #   - layout.rs (RAM_BASE, MMIO_BASE, IRQ_BASE)
                        #   - regs.rs (initial vCPU state)
                        #   - sysreg.rs (curated sysreg list)
  squib-fdt/            # FDT builder, vm-fdt-based
  squib-loader/         # kernel loader: Image, Image.gz, Image.zst, PE
  squib-bus/            # MMIO bus, BusDevice trait
  squib-virtio/         # virtio-MMIO transport + queue (use rust-vmm virtio-queue)
                        # subcrates: -block, -net, -vsock, -balloon, -rng, -console
  squib-gic/            # in-kernel GICv3 wrapper (calls hv_gic_*)
  squib-mmds/           # ported from Firecracker
  squib-net/            # macOS-specific vmnet integration (NAT mode)
  squib-snapshot/       # serde+bitcode state save/restore
  squib-vmm/            # the VMM core: builder, vCPU thread, device manager,
                        # event loop (kqueue via mio or polling)
  squib-api/            # Firecracker-compatible REST + JSON config
  squib-cli/            # the binary; thin CLI on top of squib-api
  squib/                # facade crate, re-exports public surface
```

The trait abstraction at the `squib-hv` layer is alioth-shaped:

```rust
pub trait Hypervisor: Send + Sync {
    type Vm: Vm;
    fn create_vm(&self, config: &VmConfig) -> Result<Self::Vm>;
    fn max_vcpus() -> u32;
}
pub trait Vm {
    type Vcpu: Vcpu;
    fn create_vcpu(&self, index: u32, mpidr: u64) -> Result<Self::Vcpu>;
    fn map_memory(&self, host: *mut u8, ipa: u64, len: u64, perms: MemPerms) -> Result<()>;
    fn create_gic(&self, vcpu_count: u32) -> Result<HvGicV3>;
}
pub trait Vcpu: Send {
    fn get_reg(&self, reg: Reg) -> Result<u64>;
    fn set_reg(&mut self, reg: Reg, val: u64) -> Result<()>;
    fn run(&mut self, ctx: &mut RunContext) -> Result<VcpuExit>;
    fn cancel(&self) -> Result<()>;  // hv_vcpus_exit
}
```

Even though squib is HVF-only, having the trait gives us: (a) clean unit-testability with a `MockHypervisor`; (b) an escape hatch if Apple ever ships a successor API; (c) layer separation that makes the snapshot crate testable without a live HVF instance. The cost is one indirection — at vCPU exit rates of low-thousands per second, immeasurable.

## 6. Synthesis C — performance reality check

The "Firecracker-class boot time" target needs sober calibration:

- **Firecracker on Linux/KVM, x86_64**: 125 ms user-space-code-running boot, well-documented. This is the *target*, achieved with PVH boot, no FDT, no UART, minimal init.
- **Firecracker on Apple Silicon**: not native. The cited 125 ms-on-M3 number is **macOS → Lima Linux VM → Firecracker** (KVM-in-Linux-VM-on-macOS). It's not measuring HVF.
- **libkrun on macOS HVF, aarch64**: no published native boot-time number from upstream. RedHat blogs focus on inference throughput. Anecdotal community reports cluster around 200–500 ms for a small Linux microVM with virtio-block + console; SSH-able guest is +1–2 s.
- **Fundamental constraints on HVF that affect cold start:**
  - No PVH boot protocol (we use FDT-and-Image, which adds ~50 ms versus PVH zero-page).
  - Userspace-emulated UART/RTC for early boot (the in-kernel GIC helps but doesn't eliminate this).
  - HVF has measurably higher per-exit latency than KVM. Microbench shows an `hv_vcpu_run` round-trip in the 1–2 µs range on M-series silicon, KVM is 0.3–0.6 µs. Multiplied by ~10⁴ early-boot exits, that's an extra 5–15 ms.

**Realistic native-HVF squib boot-time target for 1.0:**
- 250–400 ms to user-space init on M2 Pro / M3, small Linux kernel + initramfs, no virtio-fs.
- 500–800 ms with full virtio-block + virtio-net + virtio-vsock + virtio-fs.
- "Firecracker-class" in the sense of "small footprint, fast" — yes. "125 ms" — no, not natively.

Squib should **measure and publish** this from week 1 of the HVF backend coming up, rather than promise a number borrowed from a different stack.

## 7. Synthesis D — risks to plan around

1. **`applevisor` bus-factor.** Single maintainer, niche crate. If it goes unmaintained mid-Apple-OS-cycle, squib needs to fork. Mitigation: keep `squib-hv` as the only file that imports `applevisor`; never let applevisor types leak into the rest of the codebase. Total dependency surface should be <50 call sites.
2. **Hypervisor.framework symbol availability across macOS versions.** `hv_gic_*` lives on macOS 15+. `hv_vm_config_set_el2_enabled` lives on macOS 15+. Squib's stated minimum is "Apple Silicon, recent macOS"; pin this to **macOS 15 Sequoia minimum** explicitly to avoid the libkrun trap of carrying both userspace and in-kernel GIC paths.
3. **vCPU thread affinity.** HVF's "every `hv_vcpu_*` call must run on the creating thread" is a hard ABI. This forces a `std::thread::spawn` per vCPU. Mitigation: spawn at vCPU creation, communicate via mpsc channels for control plane, never try to multiplex.
4. **Codesigning + entitlement workflow.** `com.apple.security.hypervisor` is required for *any* HVF use. The libkrun project ships `hvf-entitlements.plist` in the repo root. Squib needs the same. Local dev path: `codesign --entitlements squib.entitlements -s - target/release/squib` baked into the Makefile. Distribution path will need notarization.
5. **No native dirty-page tracking.** Snapshots will require either (a) full memory copy (slow, simple) or (b) `hv_vm_protect` write-protect-and-fault for incremental dirty tracking (faster, complex, per-page-fault overhead). For 1.0 ship full-memory snapshots; revisit after.
6. **Networking entitlement.** `com.apple.vm.networking` is restricted for bridged mode; squib must default to NAT via `vmnet` shared-mode (no entitlement) and document the bridged path as "build from source + DTS request".
7. **PCI is a yak-shave.** Firecracker is virtio-MMIO-only and so is libkrun. cloud-hypervisor has PCI but it's not needed for the Firecracker API. Don't ship PCI in 1.0.
8. **vsock subtlety.** Apple's VZ has its own non-standard vsock that uses a `VZVirtioSocketDevice` rather than virtio-mmio with `VIRTIO_ID_VSOCK`. **squib uses HVF, not VZ, so this doesn't apply** — we use plain virtio-MMIO vsock. But docs/examples assuming VZ vsock will mislead users; warn in README.
9. **Cross-host snapshot impossible.** KVM↔HVF snapshot transfer is not a goal. Different vCPU state, different timer semantics, different GIC state representation. Don't promise.
10. **Rosetta-in-guest is a VZ feature.** `VZLinuxRosettaDirectoryShare` does not exist in HVF. If users want x86_64 Lambda binaries, they need binfmt_misc + qemu-user inside the guest. squib should ship a default initramfs that includes this.
11. **libkrun-style `cfg` split is tempting.** Resist. squib is HVF-only; do not introduce `cfg(target_os = "linux")` branches "just in case". It poisons the API and slows compile times.
12. **vm-fdt and other rust-vmm crates have moved.** Pin: `vm-memory = "0.17"`, `vm-fdt` (latest), `linux-loader = "0.13"`, `vmm-sys-util = "0.14"`, `virtio-queue` (latest). Don't fork the queue like libkrun did; use rust-vmm directly.

## 8. Recommendations for squib

1. **Use libkrun as the architecture template.** Apache-2.0, mature, native-macOS, actively maintained, has all the hard bits (in-kernel GIC, PSCI, ESR_EL2 dispatch). The original brief assumed LGPL; the actual license is Apache-2.0. This unlocks copying, not just reading.
2. **Adopt alioth's trait shape, not libkrun's compile-time `cfg` split.** Even though squib is HVF-only, the alioth `Hypervisor`/`Vm`/`Vcpu` traits with associated types give squib testability and a clean module boundary at near-zero runtime cost. Read `google/alioth/alioth/src/hv/hv.rs` once before writing the abstraction.
3. **Bind to HVF via `applevisor`, not dynamic loading.** libkrun's `libloading::Library` / runtime symbol resolution is overkill for a project that already requires entitlements + codesigning. Use `applevisor = "1.0"` with `features = ["macos-26-0"]`, isolate it inside `squib-hv`, never let its types escape.
4. **Port libkrun's `src/hvf/src/lib.rs` exit dispatcher verbatim.** The `VcpuExit` enum, ESR_EL2 decode, PSCI handling, and `Vcpus` callback trait are excellent and battle-tested. Translate from raw FFI to `applevisor` APIs, attribute Apache-2.0 in NOTICE.
5. **Port libkrun's `src/devices/src/legacy/hvfgicv3.rs` for the GIC.** The only complete Rust implementation of in-kernel HVF GICv3. ~150 LOC. Pin macOS minimum to 15 Sequoia and **do not** carry the userspace `gicv3.rs` fallback.
6. **Use rust-vmm crates aggressively.** `vm-memory`, `vm-allocator`, `vm-fdt`, `linux-loader`, `vmm-sys-util`, `virtio-queue`, `virtio-bindings` are the right base. Where libkrun forks (its own `queue.rs`), squib should not — depend on `virtio-queue` from upstream.
7. **Borrow virtio device implementations from cloud-hypervisor (Apache-2.0), not libkrun.** Cleaner code, better tests, current rust-vmm idioms, no fork drift. The exception is **virtio-vsock**: take libkrun's TSI implementation, it's the killer feature for AWS-Lambda-shaped guests.
8. **Port Firecracker's MMDS, dumbo, and OpenAPI server.** They are Apache-2.0 and they are the *thing* squib is matching. There is no second source.
9. **Plan the kernel loader as `linux-loader` + decompression layer.** Out of the box `linux-loader` handles raw `Image` and PE; add `flate2` for `Image.gz` and `zstd` for `Image.zst`. Don't repeat libkrun's "Image only" UX limitation on aarch64.
10. **Ship a snapshot/restore design even if v1 is dumb.** Full-memory snapshots are simple and useful. Defer `hv_vm_protect`-based dirty tracking to v1.1. Do **not** promise cross-host (KVM↔HVF) compatibility.
11. **Pin the boot-time target honestly.** "Sub-second native-HVF boot" is achievable. "125 ms" is not. Measure end-to-end on real M-series hardware and publish; treat the libkrun-and-Firecracker numbers as upper bounds from different stacks.
12. **Forbid `unsafe` outside `squib-hv`, period.** All `hv_*` calls go through `applevisor` (which is itself a safe wrapper). `#![forbid(unsafe_code)]` at every other crate root. The HVF FFI surface is the one place safe-Rust contract meets foreign code; concentrate the risk there and lock the rest of the codebase down.
